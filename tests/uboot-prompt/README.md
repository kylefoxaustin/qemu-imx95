# tests/uboot-prompt

A lean, network-free regression that the i.MX 95 **SD/eMMC boot chain reaches a
live, interactive U-Boot prompt**.

`tests/uboot/run.sh` already boots this chain, but it also drives the ENETC TFTP
datapath — so a pure *prompt* regression would be tangled up with the network
model. This test isolates the question "does the interactive prompt work" so it
can be caught on its own, cheaply, and put in `run-all.sh`.

## What it does

`run.sh` boots `ROM handover -> SM (M33) -> SPL -> U-Boot proper`, interrupts
autoboot, and types a few benign commands. The key check: it `echo`s a **unique
per-run marker** at the prompt and asserts the marker comes back — which can only
happen if the prompt actually executed the line we sent (not just printed a
banner).

**Pass:** SPL banner + U-Boot proper + the `u-boot=>` prompt + the echoed marker
returns + `printenv` is readable, with no boot anomalies (panic / abort / reset).

## Run

```sh
tests/uboot-prompt/run.sh
# PASS: U-Boot SD-boot chain reaches an interactive prompt
```

Required (override via env): `QEMU`, `SM_ELF`, `SPL_BIN`, `UBOOT_BIN` — the same
System Manager firmware and U-Boot SPL/proper binaries as `tests/uboot`. The boot
image is generated by `tests/uboot/mkbootimg.py` (no imx-mkimage needed). The
test **skips cleanly** if any artifact is absent, so it is safe in CI. The full
chain takes ~2-3 min to reach the prompt.
