# imx95 v2.6.1 — the ISP survives a second frame


A PATCH RELEASE WITH ONE REASON TO EXIST. v2.6.0 develops a raw Bayer frame
correctly and then wedges on the next one. If you are running anything that
develops frames through the ISP, move to this tag. (Capture-only paths --
CSI-2 to ISI to DRAM -- never went through the ISP and were never affected.)

THE DEFECT. TRIG_CAM0.TRIGGER was modelled as an ordinary latched bit. It is a
self-clearing command bit. The driver kicks each job with regmap_field_write(),
a read-modify-write, and regmap_update_bits() SKIPS THE WRITE ENTIRELY when the
new value equals the old. With the bit still set from the previous frame the
next kick computed "no change", no MMIO write was ever issued, the ISP was never
triggered, and the guest waited forever on a job that had not started.

Frame 0 develops perfectly; frame 1 hangs. It presents as an intermittent ISP
fault or a flaky board, not as a register that never cleared. No register cache
is involved -- the elision is in regmap_update_bits itself, and this driver sets
REGCACHE_NONE.

WHY v2.6.0's SUITE COULD NOT CATCH IT. Every test developed exactly one frame.
The defect lives entirely in the transition to a SECOND job, so no single-frame
test could reach it however thorough. It was found by a new consumer -- a batch
runner -- being the first thing to ask the model for more than one frame.

The qtest now pushes two frames through one streaming session, with a different
input for the second so "developed twice" cannot be satisfied by stale output,
and asserts the trigger reads back CLEAR -- the defect itself, not the wedged
frame it causes. Verified to FAIL against the unfixed model.

ALSO IN THIS TAG

tests/isp-batch/ -- a batch runner for a folder of raw captures: two 9p mounts
(input read-only, output writable), every frame developed through the stock
driver, outputs named after their inputs, and a receipt that names its FOLDERS
as well as its counts and ends with COMPLETE.

THREE BLIND TESTS MADE TO DISCRIMINATE, which is most of what this release is:

  - the batch staged six IDENTICAL frames and passed. That version could not
    have failed if the runner developed frame 1 six times or emitted a constant.
    Frames are now distinct and the test asserts one distinct hash per frame in
    each column.
  - the camera test fed the ISI ONE frame file, which the model rewinds and
    re-serves, so every captured frame was byte-identical at r=1.0000. It now
    stages three distinct frames and requires the capture to vary; observed
    hashes cycle 0,1,2,0,1.
  - every hash used an FNV-1a offset basis with a DIGIT MISSING. It still hashed
    and still distinguished inputs, so all internal checks passed on numbers no
    outside implementation could reproduce -- and the two sites that compared
    against each other agreed perfectly. A receipt's hash exists to be verified
    independently.

AND ONE FOR WHOEVER TOUCHES THE GUEST-SIDE TOOLS: a 9p transfer may not use an
mmap'd V4L2 buffer as its user-memory endpoint, in either direction. Reads
silently return zero bytes; writes storm "netfs: Couldn't get user pages"
forever. netfs pins pages with get_user_pages and a V4L2 mapping is
VM_IO/VM_PFNMAP. Bounce through ordinary memory both ways.

FIDELITY, UNCHANGED FROM v2.6.0: the debayer is bilinear and the block's
per-pixel arithmetic is proprietary, so this is structurally correct, not
bit-exact against silicon. Black level and white balance (OB_WB0) are applied;
gamma, colour matrix, denoise and tone mapping are not, and an enabled
unmodelled stage says so at runtime.
